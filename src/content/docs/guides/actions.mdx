Actions are the core of BeDoc's functionality. There are two kinds:

- **Parsers** read source files and produce a structured object.
- **Formatters** take that structured object and render it into an output
  format (Markdown, Wikitext, …).

An action is a JavaScript file that **default-exports a class**. That class
declares a little metadata and describes its work as a pipeline. BeDoc
discovers the action, negotiates its [contract](/guides/contracts/) against a
partner action, instantiates it, and runs the pipeline over each file.

## Anatomy of an action

Every action class has exactly two required members:

1. **`static meta`** — describes what the action is and points at its
   [contract](/guides/contracts/).
2. **`setup`** — an arrow function that receives an
   [`ActionBuilder`](#the-pipeline) and configures the processing pipeline.

```js
import { ActionBuilder, ACTIVITY } from "@gesslar/actioneer"

export default class MyParser {
  static meta = Object.freeze({
    kind: "parser",
    input: "lua",
    terms: "ref://./my-parser.yaml",
  })

  setup = builder => builder
    .do("Extract blocks", this.#extractBlocks)
    .do("Process functions", ACTIVITY.SPLIT,
      ctx => ctx,                 // splitter
      ctx => ctx,                 // rejoiner
      new ActionBuilder()
        .do("Extract signature", this.#extractSignature)
        .do("Extract description", this.#extractDescription),
    )
    .done(this.#finally)

  #extractBlocks = ctx => { /* … */ }
  #extractSignature = ctx => { /* … */ }
  #extractDescription = ctx => { /* … */ }
  #finally = ctx => ({ functions: ctx })
}
```

## `static meta`

`meta` is a frozen object. The required fields depend on the `kind`.

| Field       | Applies to | Meaning |
| ----------- | ---------- | ------- |
| `kind`      | both       | `"parser"` or `"formatter"`. |
| `input`     | parser     | The language identifier matched against `--language`. |
| `format`    | formatter  | The output format matched against `--format`. |
| `extension` | formatter  | Extension used for written output files (e.g. `md`). |
| `terms`     | both       | A `ref://` path to the action's [contract](/guides/contracts/) YAML/JSON file, resolved relative to the action file. |

## The pipeline

Instead of a single `run()` method, an action describes its work as a chain of
named steps using the fluent
[`ActionBuilder`](https://actioneer.gesslar.io/reference/action-builder/) API
from [Actioneer](https://actioneer.gesslar.io/). The `setup` field is an arrow
function (so `this` is the action instance) that receives the builder and
returns it configured:

```js
setup = builder => builder
  .do("Step name", this.#stepMethod)
  .do("Another step", this.#anotherMethod)
  .done(this.#finalize)
```

- **`.do(name, fn)`** adds a step. Each step receives the current context
  (`ctx`) and returns the context for the next step.
- **[`.do(name, ACTIVITY.SPLIT, …)`](https://actioneer.gesslar.io/guides/split/)**
  fans the context out into items, runs a sub-pipeline over each (in parallel,
  up to `--maxConcurrent`), then rejoins the results.
- **[`.done(fn)`](https://actioneer.gesslar.io/guides/done/)** registers the
  final step that produces the action's result.

:::tip[Built on Actioneer]
BeDoc's pipelines are [Actioneer](https://actioneer.gesslar.io/) pipelines. See
the Actioneer docs for the full [ActionBuilder
API](https://actioneer.gesslar.io/reference/action-builder/),
[ACTIVITY modes](https://actioneer.gesslar.io/reference/activity/),
[SPLIT parallelism](https://actioneer.gesslar.io/guides/split/), and
[nested pipelines](https://actioneer.gesslar.io/guides/nested-pipelines/).
:::

The **step names matter**: they are the anchor points for
[hooks](/guides/hooks/). A step named `"Format function"` can be wrapped by a
`before$formatFunction` / `after$formatFunction` hook (the hook name is the
camelCase of the step name).

### What a parser produces / a formatter consumes

A parser's pipeline ends by producing the structured object promised by its
contract — typically `{ functions: [ … ] }`. That object is handed to the
matched formatter, whose pipeline renders it to a string. The shape of that
object is governed by the [contract](/guides/contracts/) the two actions
negotiate.

## Logging

Actions are **not** handed a logger instance — there is no `this.log` on your
action. BeDoc's own debug output is controlled by the `--debug` /
`--debugLevel` [configuration](/start/configuration/) options.

## Packaging

A single action file default-exports a single action. To ship one or more
actions as an installable package, list the files under a `bedoc.actions` array
in your `package.json` so BeDoc can [discover](/start/discovery/) them:

```json
{
  "name": "bedoc-mylang-parser",
  "version": "1.0.0",
  "type": "module",
  "bedoc": {
    "actions": ["./bedoc-mylang-parser.js"]
  }
}
```

See the [Modules](/guides/modules/) guide for packaging and naming conventions,
and the [Parsers](/guides/parsers/) and [Formatters](/guides/formatters/)
guides for end-to-end examples.

## Hooks

Actions expose their named steps as [hook](/guides/hooks/) points, letting users
inject custom logic with `before$`/`after$` handlers — without touching the
action itself.

Read the [Hooks Guide](/guides/hooks/) to learn more.
